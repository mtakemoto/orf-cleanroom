## S1. Verified
- S1.1 Parsing the payload with the k=5 token model (q zero bits, stop bit, 5-bit suffix) consumes the whole payload to within 4 bits on every file tested in full, 6 of 6; that is a statement about those six files, not a corpus-wide bound. A bounded parse of the 87-file unassigned cohort leaves 0-7 bits before the payload end (S1.8). The row period equals W where the row-start profile is sharp; busy bodies carry more than W tokens per row. [F-period, F-end]
- S1.2 On the four 5240-wide E-M1MarkII files (ids 1993, 1995, 1997, 1998), in the first 400 width-sized token blocks, cross-field association dominates at sequential lags 1 and 3 and same-field association at lag 2; the assumed-stride vertical lag-2 L-L MI is 0.017 to 0.018 bit on three prefixes and 0.0007 on id 1993. These are token-index offsets, not established physical rows. [F-em1] A separate run reproduces the selected prefix figures on 1995/1997 and extends their full four-field tables to whole payloads: lag-1 H-to-L falls from 0.0390/0.0394 to 0.0280/0.0281 bit. Smaller off-pattern cells are nonzero; within-token H/L MI is 0.0005 in the prefixes and 0.0007 whole, versus baselines printing 0.0000. This supports alternating association, not literal cross-/same-field exclusivity, exact independence, CFA identity or a decoder rule. [F-lags-full]
- S1.3 With the same parse, b4 of one token carries 0.95 to 0.98 of the baseline-adjusted information between H of that token and L of the next, on E-M1MarkII ids 1993 (5240 wide) and 1994 (10400 wide), 400-row prefix and whole payload. The amount of that information differs by file: about 0.05 bit on id 1993, 0.09 to 0.11 bit on id 1994. [F-b4b2]
- S1.4 With the S1.1 parse (k=5, stop bit 1, escapes parsed like any token), whole payloads, tokens parsed divided by payload width x height is 1.027 to 1.036 on four CC0 files from bodies not 5240 wide (E-P3 and E-PM1 4080x3040: 1.0271, 1.0287; E-M1 4640x3472: 1.0363; E-M10 Mark IV 5200x3904: 1.0287) and 1.155 on TG-7 (4040x3016, 1.1552), the busiest of the five by bits per pixel. Escapes (q >= 17) per file: 1606 to 25462 (TG-7 the most), 0.008% to 0.18% of tokens. Scope: Partial, item 2 of lead #29 on these five files only; the lead's calm 5240-wide figures are tested separately in S1.6, and the E-M1 value is slightly outside the lead's 4640-wide range (1.025 to 1.034). [F-tpp]
- S1.5 On three further whole CC0 payloads from bodies lead #37 did not use (E-M1MarkII 1993, OM-1 5283, OM-5MarkII 8549), the first five payload bytes are `00 00 00 00 01`, an initial q=39 token. Exactly one q=39 occurs in each payload, so only at the start; no q=30 occurs and non-initial escapes lie at q 17 to 28. Escape rate rises with bpp (13, 11074 and 24213 escapes at 6.151, 6.913 and 7.836 bpp), and the two escape-rich files peak at q=21. [F-q39]
- S1.6 Whole-payload tokens per pixel on the 5240-wide and 5220-wide bodies not covered by S1.4: 1.00130 on E-M1MarkII id 1993 (5240x3912, 6.151 bpp), 1.03952 on OM-5 Mark II id 8549 (5240x3912, 6.913 bpp) and 1.12756 on OM-1 id 5283 (5220x3912, 7.836 bpp). The lead's 1.0013 calm figure reproduces on id 1993, but id 8549 is also 5240 wide and is not calm, so "calm" is not set by payload width alone; the lead's 1.154 for a 5220x3912 body does not reproduce on id 5283. Across these three the ratio rises with bpp, consistent with S1.4. Scope: Partial, item 2 of lead #29 on these three files only; items 1 and 3 to 9 not verified. [F-tpp5240]
- S1.7 **Shared unassigned-cohort observation, not a V1 signature:** across the 87 distinct CC0 variable-size hashes in the frozen pre-lead cohort, 82 payloads end in a 1 bit and five in a 0 bit; the longest final run is 10 bits. The corrected final-byte, final-eight-byte and full-payload histograms reproduce exactly. A final-byte count is capped at eight, combining seven exact-eight runs and two ten-bit runs. These counts alone do not identify the endpoint or a padding rule; S1.8 measures the endpoint. Scope: this same 87-file cohort, not unseen-body validation. [F-tail]
- S1.8 **Endpoint and terminal-run composition (shared unassigned cohort, not a V1 signature):** with the same k=5 parse, accepting a token only when its q + 6 bits fit inside the payload, the parse ends 0-7 bits before the payload end on all 87 files. Residual-length histogram: 0: 11, 1: 8, 2: 17, 3: 17, 4: 14, 5: 14, 6: 4, 7: 2. The full-payload trailing run equals the trailing ones of `[preceding suffix if q = 0] + q zeros + stop + suffix + residual` on 87 of 87. The five zero-ending files (1431, 2152, 5286, 6345, 7802) are the five whose residual ends in 0; the ten-bit runs (3210, 6343) are 2 residual 1s + six 1s from q = 0, suffix 31 + two 1s from the preceding suffix. The residual bits are outside the last complete token, but whether they are encoder padding or a truncated final token is not established. Scope: this same 87-file cohort; the upstream `orf_tokens.scan` at a3fdd6f read a suffix past the payload on six files (1079, 2150, 7266, 7796, 7798, 7801), which the bounded parse used here rejects. [F-end]

- S1.9 **Shared six-file suffix-only observation, not a V1 signature:** in the fixed 262144-token prefix experiment (128-token blocks, complete escape-containing blocks omitted, three suffix-only mappings, both lane counts) on public ids 1993, 6343, 5283, 1998, 6347 and 7262, none of the 36 pooled bridge-energy cells is at or below 0.5. The signed_digit range across both lane counts is 0.624050 to 1.091014; the earlier Claim minimum 0.618104 was a transcription from an exploratory file outside this cohort. The signed_digit one-lane values on 1993 and 1998 are below the permutation mean. Scope: the original Partial bridge-energy experiment only; no value assembly, historical private growth figure or other #32 reading is verified. Metric/tool design: @mtakemoto, #64. [F-bridge, F-bridge-range]

## Gaps
- G1. **Value assembly:** how q, H and L (labels for the bit groups b4b3 and b2b1b0) combine into a value. No signed or other reading of L is established by measurement. Suffix-only signed_digit bridge energy is below the permutation mean on two of the six public files (S1.9), but no value assembly is established; the original Partial scope and all other #32 questions remain open. To test: take tokens from several CC0 V1 files, tabulate (q, suffix) against neighbouring-pixel differences, and test candidate assemblies for consistency with a smooth image.
- G2. **Predictor:** which neighbours the residual is relative to. No predictor is established; testing by integrating along rows is one way. To test: fit candidate predictors (left, up, mixtures, odd/even rows or columns) to partly assembled values; the right one gives a markedly narrower residual distribution.
- G3. **Row stride drift:** on some bodies the per-row token count drifts instead of staying equal to the width (S1.1 notes busy bodies exceed W). Why? To test: list the manifest files with `row_stride` drift, measure per-row token counts, and check for row headers, padding or per-row byte alignment. This may split the variant.
- G4. **Horizontal offset ramp:** the alignment offset with the preview grows with row band. Is that an artefact of the alignment method or real?
- G5. **Reproduction starting files:** good files for the #11 parse are the 5240-wide payloads: raw.pixls.us ids 6343 (OM-5), 8549 (OM-5 Mark II), and the 5240-wide E-M1MarkII files, all CC0.
- G6. Hypothesis H1: one shared decompression scheme across most compressed ORF bodies, with per-model differences limited to dimensions, crop, levels, white balance and colour (hypothesis, unverified; not evidence). Source: a general AI-assistant summary of unknown provenance, so it carries no weight here. Our own measurements so far show at least two bitstream behaviours (V1 and V2 in VARIANTS.md), and there may be many more (per model, firmware or mode). To test: classify every manifest file and see whether V2 reduces to V1 under some parameter, or whether more variants appear. See also [V2.md](V2.md).
- G7. Hypothesis H2, High Res Shot files need separate handling (hypothesis, unverified; not evidence), is recorded in [V0.md](V0.md) G5 but applies here too: 19 of the 21 High Res Shot files in the manifest are compressed. To test: compare the token parse and row stride of a High Res Shot file with a normal-mode file of the same body.
- G8. **Suffix width on TG-7:** in a whole-payload scan with suffix width k = 2 to 8, tokens per pixel is nearest 1 at k=5 (stop bit 1) on four of five files (1.027 to 1.036), but on TG-7 k=6 gives 1.0006 against 1.155 for k=5 [F-tpp]. Either TG-7 uses a different suffix width, or the k=6 value is coincidence, or the busy-body excess over one token per pixel (S1.1, G3) is what k=6 absorbs. The scan script was not committed. To test: a `tools/` version of the k scan; run it on TG-7 and other busy bodies and check whether the k=6 parse still consumes the payload to within a few bits (S1.1) and whether its escape count, q histogram and neighbour dependences (S1.2) look like a code or like noise.
- G9. **Lead #29 item 1 has no defined measure:** "only k=5 gives zero change in bits consumed per row" needs rows delimited in the token stream, and no row boundary is known (G3; `tools/orf_tokens.py` has no suffix-width option, F-tpp). Anyone taking item 1 must first define a per-row measure (for example how row starts are located and what "bits consumed per row" is counted from) and say how it works without row delimiters, before running k = 2 to 8 with both stop-bit conventions. Until then item 1 is untested; the whole-payload tokens-per-pixel scan of G8 is a different measure and neither confirms nor contradicts it (it does not separate the stop-bit conventions either: k=5 with stop 0 gives 0.973 to 0.999 on the four ordinary files).
- G10. **Payload endpoint and terminal ones:** the counting part of lead #87 is verified [F-tail], and the endpoint is measured [F-end]: the bounded k=5 parse ends 0-7 bits before the payload end, and the terminal run is fully composed of those residual bits plus the last token (plus the preceding suffix when q = 0); see S1.8. Still open: whether the residual bits are encoder padding or the start of a truncated final token, and the cause of the zero endings beyond "the residual ends in 0". A file with a known end marker or a fixed padding fill would settle it.
